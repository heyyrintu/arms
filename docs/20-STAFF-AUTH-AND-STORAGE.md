## Authentication controls

- Salted scrypt password hashes: N=131072, r=8, p=1; 16-byte random salt, 64-byte key. Exact password preserved, 15-character minimum at account creation, maximum 1024 UTF-8 bytes. Password derivations are capped at two concurrent operations per app process to bound memory pressure. No plaintext/default password or public self-registration.
- Shared PostgreSQL login limits: five attempts per normalized login ID per 15 minutes, plus 60 global login attempts per 10 minutes. Global caps avoid trusting spoofable forwarded IP headers. These conservative caps require operational review/load checks before enabling real staff access.
- Unknown/malformed hashes take a dummy scrypt verification path; invalid credentials return a generic error. Database/server/provider errors and submitted credentials are not logged to the browser or console.
- Password acceptance creates a challenge, not an authenticated session. Six-digit cryptographically random code, 10-minute expiry, five guesses, one active challenge per user. Only a keyed HMAC is stored; it is bound to the opaque challenge and server secret. Email acceptance must succeed before a challenge can verify. A failed/uncertain send invalidates the challenge and returns an error.
- One-use code consumption/session creation is transactional; failed guesses commit. Challenges/session tokens are independent 32-byte random values, stored as SHA-256 hashes in the database. Only opaque cookies reach the browser. JSON never returns tokens, email addresses, hashes or codes.
- Production always requires an email-verified session, regardless of `STAFF_DEV_SKIP_EMAIL_CODE`. The optional development switch is honored only with `NODE_ENV=development`; test/production default to verification. Codes are never printed in a development console.
- Sessions: eight-hour absolute maximum, 30-minute idle expiry, live active-account/auth-version/role checks on every authorization. Logout revokes the database session. Role/password/email changes must increment `auth_version` to invalidate old sessions/challenges; operator procedures are required until audited staff administration exists.
- POST requests require the configured exact Origin, reject cross-site requests, and bound JSON bodies to 4096 bytes. Production requires an HTTPS app origin and Secure, HttpOnly, SameSite=Strict, host-only cookies. Staff pages/APIs are no-store and no-index. The eventual reverse proxy must also enforce request/body timeouts and trusted network configuration.
- No applicant/PII dashboard, export or CV download action is implemented. Future record-level assignment checks are required in addition to role checks. No privileged operation may rely solely on hiding a button or checking a layout.

Email is an additional verification step, not phishing-resistant or NIST-assured MFA. NIST excludes email as an out-of-band authenticator. The owner requested email codes; stronger TOTP/passkey options can be assessed separately. [NIST SP 800-63B](https://pages.nist.gov/800-63-4/sp800-63b.html), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

## Setup and secrets

Keep `STAFF_AUTH_ENABLED=false` until all gates below pass. `.env` is ignored and mode 600. `DATABASE_URL` is the operator/bootstrap connection; `STAFF_DATABASE_URL` is restricted and locally uses the approved SSH tunnel. Do not use the operator URL in browser code or the authentication pool. Runtime refuses an elevated/owner account, memberships that allow privileged/owner roles, and table/column grants that permit staff credential/role changes. `npm run check:staff-database` reports safe read-only permission/count status over the approved connection. No service secret may use a `NEXT_PUBLIC_*` variable.

1. Open the approved tunnel with `npm run db:tunnel` when local DB access is needed. Close with Ctrl+C. It binds loopback only and does not open the public DB firewall.
2. Inspect `npm run db:staff:plan` without DB writes. Setup was already applied; existing-resource detection deliberately refuses a second application. Future changes require new reviewed migrations, not editing the applied files.
3. The owner must choose the first staff login ID, actual reachable staff email and role. Use an interactive terminal with the operator connection and the command below. It prompts twice for a hidden password, hashes it, and inserts one account without altering an existing account. Never put the password in chat, command arguments or a seed file.

```sh
npm run staff:create -- --ssh-tunnel --login-id OWNER_CHOSEN_ID --email OWNER_CHOSEN_EMAIL --role admin
```

4. Set `APP_BASE_URL` to the actual local development origin or approved production HTTPS origin. The official production domain has not been inferred from the email domain.
5. Configure regional SES identity and restricted send permissions. Set `SES_REGION` and `SES_FROM_EMAIL=noreply@armstalentpartners.com`. Dedicated `SES_ACCESS_KEY_ID`/`SES_SECRET_ACCESS_KEY` or an approved workload role must allow only `ses:SendEmail` for the approved identity and FromAddress. Lightsail bucket resource credentials are separate and do not confer SES access. Do not reuse broad AWS root/admin credentials.
6. Confirm sender/domain authentication (DKIM/DMARC), testing restrictions/production access, delivery to approved staff addresses, bounce handling and monitoring. SES API acceptance is not proof of inbox delivery. The app returns an error if API acceptance fails; never bypass email verification to work around delivery problems. [SES identity verification](https://docs.aws.amazon.com/ses/latest/dg/creating-identities.html), [SES production access](https://docs.aws.amazon.com/ses/latest/dg/request-production-access.html).
7. Test the full browser sign-in/verify/logout flow with approved staff, wrong/expired/replayed codes, disabled/revoked accounts and real restricted runtime credentials. Then explicitly enable staff authentication in the intended environment. This does not enable public collection or authorize deployment.

Native-form header regression: the local setup helper uses `Referrer-Policy: strict-origin-when-cross-origin`. Do not solve this by trusting null/missing origins or skipping CSRF/cookie checks. The corrected policy preserves the expected Origin and keeps credentials in the POST body; the page loads no third-party resources.
